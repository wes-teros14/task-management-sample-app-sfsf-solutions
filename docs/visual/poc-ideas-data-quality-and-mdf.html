Next POC options: #3 and #4

Two follow-ups that build on the onboarding sample. Each one reuses approuter, XSUAA, the Destination service and SF OData, and adds one new BTP or SF concept, highlighted in purple. Items marked unverified are from general knowledge and haven't been checked on this trial or tenant.

#3 Data quality checker

What it does: on a schedule, it scans SF for employee records with missing or invalid data (for example a blank gender, which is the real gap that caused the "Mandatory value is missing for gender … userId:200543" error), creates a To-Do for the responsible HR admin, and shows a dashboard of open issues.

The big new lesson: no user is logged in. The onboarding app works because a person logs in and the SAML bearer flow passes their identity to SF. A scheduled job has no person, so the destination has to authenticate as a technical user (an SF API user with RBP rights to read everyone's data). The sap-successfactors-extensibility service accepts a technicalUser parameter for this (unverified, check SAP docs), or you can create a separate destination. The endpoint the scheduler calls is secured with an XSUAA client-credentials token, not a user JWT.

Example rules (configurable list)

Field names depend on the tenant's data model. Check them against $metadata on apisalesdemo8 first.

Build outline

  1. Rules engine: each rule is an entity, a filter and a message. Start with 2 rules.
  2. Paging: follow SF's __next link or use $top/$skip. This fixes the cut-off this sample has with GET User.
  3. No duplicates: before creating a To-Do, check that an open one doesn't already exist (name pattern "DQ: <rule> (<userId>)"), or store run results in the app's own DB.
  4. Create To-Dos: POST TodoEntryV2 with category 41, the same call that's proven to work, owner = HR admin, linkUrl = the employee's profile.
  5. Scheduling: bind the BTP Job Scheduling service and register a job that calls POST /jobs/run. Simpler fallback with no new service: Spring @Scheduled or a CAP timer. That's fine for a POC, but it has no UI, no run log, and runs on every instance.
  6. Dashboard: open issues per rule, last run time, and a "Run now" button.

New BTP skills

Job Scheduling service, client-credentials auth, technical-user destination, (optional) own DB for run history.

New SF skills

Effective-dated entities (PerPersonal, EmpJob), eq null filters, paging, RBP for API users.

Demo story

"Last night the job found 37 records missing gender. Each HR owner got a To-Do with a direct link to fix it."

Risks and checks: Job Scheduling on BTP trial isn't verified, so check the trial entitlements. The technical user needs broad RBP read rights. Without deduplication you can flood people with To-Dos. Large tenants need paging and throttling.

#4 Custom MDF object app

What it does: a BTP app for create/read/update/delete on a custom SF object you define. Example: Equipment Request. An employee requests a laptop or phone, the manager approves, and IT sees the queue. The data lives in SF as an MDF object, so it shows up in SF reporting, permissions and workflows.

Example object: cust_EquipmentRequest

FieldTypeNotes
externalCodeAuto numberKey
cust_employeeUserWho it's for. The default is the logged-in user, through principal propagation like today.
cust_itemTypePicklistLaptop / Phone / Monitor
cust_reasonString
cust_neededByDate
cust_statusPicklistSubmitted / Approved / Rejected / Fulfilled

Keep it not effective-dated for the POC, so you don't have to manage effectiveStartDate in every call.

Build outline

  1. Define the object in SF: set API visibility to Editable, then grant RBP permissions to the roles involved.
  2. Get the metadata: GET /odata/v2/cust_EquipmentRequest/$metadata → save to edmx/. Use the same VDM generator as this repo, or cds import in CAP.
  3. Read: GET cust_EquipmentRequest?$filter=cust_employee eq '<me>', with picklist labels via $expand on the picklist navigation.
  4. Create: POST cust_EquipmentRequest. Generated MDF entities support normal create, so no hand-built upsert is needed. The reverse of this sample's To-Do case is unverified for this tenant.
  5. Update status: MERGE or upsert. Manager and IT views filter on status.
  6. Optional: attach an SF workflow to the object, so approval happens in SF's own inbox and the app just shows the status.

New SF skills

MDF object design, picklists via OData, object API visibility, MDF RBP, (optional) workflow on MDF.

New BTP skills

Regenerating the client when the object changes. A good fit for CAP + Fiori elements: a CRUD UI from annotations, with little hand-written UI.

Demo story

"Request equipment in a modern app, approve it in SF, and it shows up in SF reports. No separate database."

Risks and checks: you need Admin rights on apisalesdemo8 to create objects (Configure Object Definitions). After changing the object, refresh SF's metadata cache (OData API Metadata Refresh) and regenerate the client. Picklist and user-field navigation names differ per tenant, so read them from $metadata.
