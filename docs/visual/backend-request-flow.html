What the app is

This is SAP's sample "Employee Onboarding" extension for SuccessFactors, running on BTP Cloud Foundry. A manager picks an employee, and the app creates an SF To-Do (TodoEntryV2, category 41) for that person, owned by the manager. The manager can then list, complete or delete those To-Dos. The app has no database of its own: SF is the only store. It is a proof of concept.

The people you can pick are existing SF users, since GET User has no filter. "Onboarding" is only the label on the To-Do, which points at the employee through subjectId. The app never reads SF Onboarding or new-hire data.

BTP building blocks

The pieces deployed into the Cloud Foundry space (org 63f955d7trial, space dev). Apps are running code. Service instances are managed BTP services. A binding connects an app to a service and puts that service's credentials into the app's VCAP_SERVICES environment variable.

App

approuter-task-management

Node @sap/approuter. It is the only public entry point. It logs the user in through XSUAA, keeps the session, and forwards every request to the Java app with the user's JWT attached (xs-app.json, forwardAuthToken: true).

App

task-management

Spring Boot jar on java_buildpack (Java 11). It serves the SAPUI5 UI and the /v1/* REST API, and calls SF.

Service · bound to both apps

xsuaa

BTP's OAuth server. It issues the user's JWT after login. The Java app uses the binding to check that the JWT signature is genuine.

Service · bound to Java app

destination

BTP's address book for remote systems. It stores the SF URL and auth method, and hands out ready-to-use SF tokens at runtime.

Service · bound to Java app

sap-successfactors-extensibility

Links BTP to the registered SF system ("SFSF Demo"). Creating it auto-creates a destination with the same name, using OAuth2SAMLBearerAssertion.

How a request travels

One request, step by step: "New Request" for Barbara Kent

  1. Browser
    The UI sends POST /v1/onboardings with the selected user (userId 100113) to the approuter URL.
  2. approuter + XSUAA
    With no session, the user is redirected to XSUAA to log in. Afterwards the approuter stores the user's JWT in the session.
  3. approuter
    It forwards the request to token-destination, which is the Java app's URL from manifest.yml, with Authorization: Bearer <JWT>.
  4. Java · SecurityConfiguration
    Spring Security checks the JWT against the xsuaa binding and rejects the request if it's missing or invalid. UserInfoImpl reads the logon name (davidm.epiuse).
  5. Java · ToDoEntityManagerImpl
    It builds the To-Do: name "Barbara Kent (100113)", status 2, category 41, subjectId 100113, due today + 7 days, owner userNav → User('davidm.epiuse').
  6. Java · DestinationProvider → Destination service
    It reads VCAP_SERVICES to find the extensibility service's name, then asks the Destination service for the destination with that name, passing the user's JWT.
  7. Destination service → SF
    Because the auth method is OAuth2SAMLBearerAssertion, it builds a SAML assertion that says "this is davidm.epiuse" and exchanges it at SF's /oauth/token for an SF access token for that user. This is principal propagation.
  8. Java · Cloud SDK (VDM)
    It sends POST https://apisalesdemo8.successfactors.com/odata/v2/TodoEntryV2 with the SF token. SF creates the entry (ID 257507) and the app returns 201.

The two tokens (the core BTP idea)

Token 1 · BTP side

XSUAA JWT

Proves to the Java app who the user is. It's issued by XSUAA at login and carried by the approuter. SF never sees it.

Token 2 · SF side

SF OAuth access token

Proves to SuccessFactors who the user is. The Destination service gets it by exchanging a SAML assertion built from Token 1. The app never handles SF passwords or keys.

Because both tokens name the same person, SF permissions (RBP) apply per user, and the app's userId eq '<me>' filter works. The XSUAA logon name has to equal the SF userId, which it does here: davidm.epiuse.

Inside the Java app

rest/*Controller→ services/*Manager (impl)→ VDM services (DefaultToDoEntityService, DefaultUserService, DefaultPhotoService)
or CustomODataToDoEntryServiceImpl for upsert→ .executeRequest(destinationProvider.getDestination())
  • VDM: typed Java classes generated at build time from edmx/ToDoEntity.edmx, User.edmx, Photo.edmx and upsert.edmx into target/vdm.
  • Upsert is hand-built: the generated classes don't cover the upsert function import, so CustomODataToDoEntryServiceImpl builds the request with Gson and an ODataRequestAction.

Endpoint map: app call → SF OData v2

App endpointSF OData v2 callNotes
GET /v1/onboardings GET TodoEntryV2?$select=…&$filter=categoryId eq '41' and userId eq '<me>' No status filter, so active (2) and completed (3) both come back. Java then drops names that don't match Name (id).
POST /v1/onboardings POST TodoEntryV2 Sends todoEntryName="Full Name (id)", status=2, categoryId="41", subjectId=selected employee, dueDate=now + 7 days, linkUrl="https://sap.com", userNav→User('<me>').
PATCH /v1/onboardings/{id}/complete POST upsert body {"__metadata":{"uri":"TodoEntryV2(<id>M)"},"status":3} Fails unless every upsert result is OK.
DELETE /v1/onboardings/{id} DELETE TodoEntryV2(<id>M) Hard delete.
GET /v1/users GET User?$select=defaultFullName,email,userId,title,department Has no filter and no paging code.
GET /v1/users/current, /{userId} GET User('<id>') + GET Photo(photoType=1,userId='<id>') A 404 on either call is ignored.
GET /v1/users/{userId}/photo GET Photo(photoType=1,userId='<id>') photoType 1 = live profile photo.

Verified in this deployment (2026-10-23)

  • The write reached SF: Postman GET TodoEntryV2?$filter=categoryId eq '41' and subjectId eq '100113' returned todoEntryId 257507, userId "davidm.epiuse", status 2, and due date 1793318400000 = 30 Oct 2026, which is creation date + 7.
  • Destination auth is OAuth2SAMLBearerAssertion (checked in the BTP cockpit).
  • SF system: apisalesdemo8.successfactors.com, the only system in use.

Things to know

  • Completed requests stay in the list on purpose: the UI shows them as "Completed" and hides the ✓ button (App.controller.js:180, :213).
  • User list is cut off: GET User has no paging code, so only the first page SF sends back is returned.
  • Not on David's SF home page yet: To-Do 257507 exists in SF, but it doesn't show in David's SF UI. The cause is still unknown. Possibilities: category 41 isn't shown on the home page, or the home page is caching. Still under investigation.
