What the app is

What is this app?

It is SAP's sample "Employee Onboarding" side-by-side extension for SuccessFactors, running on BTP Cloud Foundry. A manager picks an employee, and the app creates an SF To-Do (TodoEntryV2, category 41) owned by the manager. The manager can then list, complete or delete those requests. The app has no database of its own: SF is the only store. It is a proof of concept.

Why are the people in the "New Request" list already hired?

By design. GET /v1/users calls GET /odata/v2/User with no filter, so it returns every existing SF user (UserManagerImpl.getUsersProfiles). "Onboarding" is only the label on the To-Do (subjectId = the picked user). The app never reads SF Onboarding or new-hire data.

Where is the app in the repo, and what language is it?

It has three parts. The backend is Java 8 source (built and run on Java 11) with Spring Boot 2.2.1 and SAP Cloud SDK, in task-management-app/src/main/java/com/sap/core/extensions/taskmanagement/. The UI is SAPUI5, written in JavaScript with XML views, in task-management-app/src/main/resources/static/, and the Spring Boot jar serves it. The approuter is Node.js config only (approuter/package.json, xs-app.json), with no code of its own. BTP wiring is in manifest.yml, xsuaa.json and sap-successfactors-extensibility.json. The SF API definitions are in task-management-app/edmx/.

Backend and SuccessFactors APIs

How does the app log in to SF, and how is it the right user?

There are two tokens. The XSUAA JWT proves the user to the Java app. The Destination service (OAuth2SAMLBearerAssertion, confirmed in the cockpit) turns that JWT into a SAML assertion and exchanges it at SF /oauth/token for an SF token for the same user. This is principal propagation. SF permissions apply per user, and the XSUAA logon name must equal the SF userId (here davidm.epiuse).

Did "New Request" really write to SF? It's not on David's SF home page.

Yes. Postman GET TodoEntryV2?$filter=categoryId eq '41' and subjectId eq '100113' on apisalesdemo8 returned ID 257507, userId "davidm.epiuse", status 2, due 30 Oct 2026. Why it doesn't show in the SF UI is still open (2026-10-23). The suspected causes are category 41 not being shown on the home page, or caching.

How does the backend talk to SF?

Each REST call in /v1/* maps to one SF OData v2 call, made with SAP Cloud SDK typed classes (VDM) generated from task-management-app/edmx/*.edmx. The SF URL and credentials come from the Destination service, through the sap-successfactors-extensibility binding. "Complete" uses the upsert function import, which is hand-built with Gson because the VDM doesn't cover it, with body {"__metadata":{"uri":"TodoEntryV2(<id>M)"},"status":3}. The current user's XSUAA logon name is used directly as the SF userId. The full endpoint-to-OData table is in docs/visual/backend-request-flow.html.

Does the onboarding list show completed requests?

Yes. GET /v1/onboardings filters only on categoryId eq '41' and the owner userId, not on status (ToDoEntityManagerImpl.getAllToDoQueryHelperFilteredByCategory). It then drops entries whose name doesn't match Name (id).

The first answer called this a "thing to watch", as if it were a gap. That was wrong. It is intentional: the UI marks status-3 entries as "Completed" and hides the ✓ action (static/controller/App.controller.js:180, :213). Lesson: read the frontend before calling backend behaviour a problem.

Where do I change the To-Do category ("event type")?

Change one constant: ToDoEntityManagerImpl.java:32 GENERIC_INTELLIGENT_SERVICES_CATEGORY. It drives both create (line 122 sets categoryId) and list (line 150 $filter=categoryId eq '<value>'). Complete and delete use only the To-Do ID. Side effects: To-Dos with the old category disappear from the list (categoryId is sap:updatable="false" in ToDoEntity.edmx:61, so they can't be moved), and method names saying "GenericIntelligentServices" become misleading. Not verified: whether SF allows API creation of categories other than 41. On 2026-10-23 the value was changed to "19" locally (not yet deployed or tested). To redeploy: mvn clean install then cf push task-management --vars-file vars.yml.

Build and deploy

Why did the build fail on JDK 26, and why did the deploy fail on sap_java_buildpack?

On JDK 26, Lombok didn't run, which caused missing-getter errors in the generated VDM. The cause is the old Lombok that Spring Boot 2.2.1 pins, plus JDK 23+ no longer running annotation processors by default. Building with JDK 11 fixed it. On the CF trial landscape (ap21), sap_java_buildpack no longer exists, so manifest.yml now uses java_buildpack with JBP_CONFIG_OPEN_JDK_JRE: '{ jre: { version: 11.+ } }'. Verified on 2026-10-23.

Will this type of app stop working on April 12, 2027?

No. The deadline is for the cflinuxfs4 stack, the Ubuntu 22.04 base image the app runs on. It isn't about the app type. From the cf push warning on 2026-10-23: new pushes on cflinuxfs4 end April 12, 2027, and restage/update ends May 10, 2027, but "at no point in time is the availability of your running application at risk". The fix is to deploy on cflinuxfs5 (e.g. stack: cflinuxfs5 in manifest.yml). java_buildpack and nodejs_buildpack both exist for cflinuxfs5 here. Not yet tested: the cflinuxfs5 java_buildpack is v5.0.7, a newer major version, and the Java 11 setting may need adjusting.

The POC idea list (idea #7) bundled "rebuild in CAP" with the stack deadline, which made it sound like the app type was ending. They are separate. A stack move is enough to keep deploying, and CAP is optional.

Can we still build Java / Spring Boot apps like this one?

Yes. Java and Spring Boot on CF is fully supported. For a new app, use current versions: Spring Boot 3, Java 17/21 and SAP Cloud SDK 5, instead of this sample's Spring Boot 2.2.1 / Cloud SDK 3.46 / Java 8 source. Spring Boot 3 runs on sap_java_buildpack_jakarta or java_buildpack. The architecture stays the same: approuter, XSUAA, Destination, Cloud SDK.

What's the advantage of recreating this in CAP, and does it work on BTP Trial?

CAP turns the SF EDMX into a CDS model (cds import) and calls SF through the same destination, so you write much less code. It also runs locally with a mocked SF (cds watch), which this app can't do. Auth is declarative (@requires/@restrict), cds add xsuaa,approuter,mta generates the BTP config, and it can generate a Fiori elements UI from annotations. Downsides: you have to learn CDS, and the SF upsert function import still needs a custom handler. Trial: CAP is open-source libraries, so it runs on trial CF. Business Application Studio and HANA Cloud are available on trial (based on general knowledge, not checked in this subaccount). SQLite is enough if no local data is needed.

Where can we find a CAP-based guide?

Start with the official docs at https://cap.cloud.sap/docs/ (mirror cap.js.org), especially "Consuming Services" (/docs/guides/services/consuming-services) for cds import of SF EDMX. The closest sample to this project is https://github.com/SAP-samples/cloud-sf-extension-cap-sample, a CAP-based SF side-by-side extension (repo existence confirmed with git ls-remote on 2026-10-23; contents not reviewed). Other samples: https://cap.js.org/get-started/samples.

Do I need a new repo to build a new extension app?

It isn't required by BTP, but a separate repo is recommended for an independent app, because it gets its own build, version history and deploy cycle. What has to be different in BTP is the CF app names and routes in manifest.yml, and the xsappname in xsuaa.json (this repo uses extension-app, which must be unique in the subaccount). The destination and sap-successfactors-extensibility instances can be shared by binding them to the new app too. Use a single repo (MTA/monorepo) only when the apps are released together.

For POC #4 (Equipment Request MDF app), what are the pros and cons of CAP + Fiori elements vs Spring Boot + UI5?

CAP + Fiori elements: much less code (cds import of the EDMX, UI generated from annotations), a local run with a mocked SF (cds watch), and declarative auth. It is SAP's current recommended path, and Node v22 is already installed. Cons: Fiori elements edit screens need drafts, which need a database even when SF stores the data (workaround: in-memory SQLite). Delegating to SF needs custom handlers, $expand and value help across the remote service are limited, and the UI is opinionated. Spring Boot 3 + UI5: it reuses this repo's proven pattern (Cloud SDK, destination, principal propagation), gives full control and has no draft/DB issue. Cons: every controller, DTO, view and value help is written by hand, there is no local run without SF, and it needs JDK 17+ (only JDK 11 is set up here). Recommendation (2026-10-26): CAP for a one-object CRUD POC. Spring Boot if a custom UI or the lowest risk matters more. The draft/DB point and remote $expand limits are from general CAP knowledge, not yet tested here.
